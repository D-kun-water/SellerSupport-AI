# PRD：数码配件客服与商品改进工作台

版本：v1.3 · 2026-10-15。本文是当前范围的主文档，由早期规格结合现有代码修订。功能存在、工程回归通过、外部集成可用和业务收益成立是不同状态。

## 1. 目标、用户与边界

目标：帮助客服根据可追溯的商品、政策和授权订单处理咨询，把重复问题交给有权限、有责任人的改进流程。

主要使用者是客服与主管；商品运营和业务负责人通过现有角色参与。当前系统只实现 `agent`、`supervisor` 两种账号角色，没有独立运营、供应链或超级管理员权限模型。

当前为本地单商家应用。首次启动业务库为空，需要初始化商家、人员及资料。多份本地数据库不等于多租户。外部消息发送、支付退款、发货及承运商查询均未连接；操作人需要在原渠道执行并登记凭据。

本版不提供全网选品、广告投放、自动发布、自动采购、通用客服全渠道平台或多 Agent 自主编队。商品比较、自动取消订单、广泛故障诊断等早期规划不列为当前已交付能力。

## 2. 用户成功条件

1. 客服能够从咨询原文找到适用商品与政策，补齐必要条件，核对草稿和来源后记录处理结果。
2. 售后提案经过有权限的主管审批；版本或订单变化时不能继续使用旧批准；未知结果进入对账。
3. 人工交接保留上下文并指定负责人，交接后由当前负责人处理，支持结案和重开。
4. 客户反馈能够关联原文、专题、原因核验、改进任务、知识版本和后续观察。
5. 没有足够资料、权限或后续记录时，明确保留未知或数据不足，不用模型补造业务事实。

这些是行为验收条件。真实团队节省时间、降低错误或愿意付费仍需单独验证，见 [指标与业务验证](05_指标与业务验证.md)。

## 3. 角色与权限

| 操作 | 客服 | 主管 | 关键限制 |
|---|---|---|---|
| 创建、查看与处理工单 | 本人或有权限的关联任务 | 可查看授权范围内的团队任务 | 订单访问同时检查订单授权 |
| 编辑、复制、记录回复 | 当前允许处理者 | 当前允许处理者 | 已结案先重开；人工交接期间检查负责人 |
| 提交退款或补发提案 | 可以 | 可以 | 关联已授权订单，校验金额或订单行 |
| 批准或拒绝提案 | 不可以 | 可以 | 申请人不能批准本人提案 |
| 登记已批准提案的执行结果 | 可以 | 通过主管的对账职责处理未知结果 | 批准绑定版本，未知状态不能直接重试 |
| 人工交接 | 发起、接单和处理 | 指派、调整和处理 | 接单人必须满足关联订单权限 |
| 反馈与改进任务 | 提名反馈、处理本人任务 | 审核、归组、分派、核实交付 | 普通人员不能修改他人的任务状态 |
| 商品政策发布、评测与管理 | 使用已发布内容 | 维护、审核、回归与发布 | 发布不绕过来源、版本和回归检查 |

身份来自服务端校验的凭据；页面角色选择不授予后台权限。初始凭据在本机随机生成或由本地配置提供，不在仓库或前端内置有效通用密码。人员记录保存凭据哈希。

## 4. 功能需求与可验收行为

### FR-01 商家初始化、人员与资料准备 · 必须

- 空业务库允许主管初始化商家和人员；至少两名人员、至少一名主管；初始化后使用各自凭据登录。
- 已有业务对象时不能重复初始化覆盖资料。初始化替换初始人员，不继续保留原初始身份的业务访问权。
- 商品、政策和订单由商家录入，测试数据不作为正常启动内容。
- 验收：新库可完成初始化，初始身份替换后不能继续登录；已有业务库拒绝再次初始化。

实现依据：[商家服务](../../app/merchant.py)、[启动回归](../../tests/test_repository_startup.py)、[商家回归](../../tests/test_merchant.py)。

### FR-02 商品、政策与来源管理 · 必须

- 商品有唯一标识、SKU、品类、地区、版本、生效时间、来源和适配规则；政策保存类型、适用范围与约束。
- 发布对象与独立核对的来源事实必须一致；草稿先审核、再执行规则回归、再发布。
- 同范围有效政策冲突、资料版本变化或回归后资料变化时阻止直接发布；旧来源和历史记录保留。
- 验收：未发布、已过期或地区不匹配资料不能作为当前查证依据；来源事实不一致时拒绝发布。

实现依据：[发布服务](../../app/catalog_api.py)、[知识版本](../../app/knowledge.py)、[知识回归](../../tests/test_knowledge.py)。

### FR-03 工单创建、导入与上下文 · 必须

- 支持手工创建及 JSON 记录批量导入；保留外部标识、原文、消息、商品、设备、用途、地区和关联订单。
- 导入先预览错误与重复情况，含错误行的批次不能提交；重复外部记录按相应业务键去重。
- 信息变化增加上下文版本，旧草稿和复制状态失效。没有订单不阻塞售前咨询。
- 验收：重复提交不重复产生同一外部工单；越权订单不能关联，旧版本修改被拒绝。

实现依据：[主接口](../../app/main.py)、[业务服务](../../app/services.py)、[工单回归](../../tests/test_tickets.py)。

### FR-04 规则查证与必要澄清 · 必须

- 根据当前任务检查商品、设备型号和用途；缺少必要信息时返回明确缺项，不给确定适配结论。
- 型号级规则只适用于其明确覆盖的组合。接口、额定功率或相似型号不能单独证明兼容。
- 商品与政策按地区、发布状态、生效时间查证；来源缺失或冲突时交人工。
- 验收：未知设备、无规则组合和失效来源保持未知；澄清轮次耗尽时交人工，不强制结案。

当前规则路由覆盖有限，不能声称理解任意业务意图或完成通用推理。[规则实现](../../app/assist.py) · [工作流回归](../../tests/test_workflow.py)。

### FR-05 订单与物流快照 · 必须

- 服务端检查人员的订单授权，未授权和不存在不通过响应区别泄露。
- 展示导入订单及物流更新时间；按参考时间计算快照新鲜度和轨迹时间差。
- 时间缺失、未来时间或过期快照不能产生确定当前状态；不得表示已外联查询承运商。
- 验收：无权限不读取订单；过期或矛盾快照转人工；退货窗口需要可靠签收时间。

实现依据：[订单服务](../../app/services.py)、[当前时间回归](../../tests/test_current_time.py)、[权限回归](../../tests/test_role_lifecycle.py)。

### FR-06 回复草稿与双向翻译 · 必须

- 无模型配置时保留规则查证、资料查看、工单和英文手工编辑。
- 可选模型接收已查证的事实范围，输出结构化草稿和内部摘要，不能改变业务状态或自行扩展事实。
- 客户原文可译为中文；中文回复可译为英文，英文编辑可同步中文。两类模型能力分别控制。
- 修改一种语言后，另一语言的旧结果失效；中文输入或翻译未完成时不复制过期英文。
- 草稿经人工核对再复制；复制和在原渠道发送的记录分别保存。生成、复制都不能等同于已发送。
- 验收：未审核候选不自动采用；上下文或来源变化使旧候选失效；翻译失败保留原文和可继续编辑路径。

实现依据：[回复模型服务](../../app/live_assist.py)、[翻译服务](../../app/translation.py)、[回复编辑器](../../frontend/src/Translation.tsx)、[翻译回归](../../tests/test_translation.py)。

### FR-07 安全信号、多项诉求与人工升级 · 必须

- 识别明确异常发热、烟雾等风险信号时停止普通排查，并提示人工处理；不得生成拆机或故障充电试验步骤。
- 安全事项优先处理，其他物流、退款诉求保留为待处理项，不自动认定已安排跟进。
- 附件待核验、证据不足或字段冲突时同样保留人工出口。
- 验收：风险事项不会继续普通查证；回复明确哪些事项尚未处理。当前支持的拆分来自已编码规则，不宣称任意多意图自动规划。

实现依据：[规则服务](../../app/assist.py)、[模型输出检查](../../app/quality.py)。

### FR-08 退款与补发申请 · 必须

- 提案关联工单、订单、政策依据、原因、创建者和版本；退款记录币种与金额，补发绑定原订单行、SKU 和数量。
- 可退金额及补发累计数量由业务规则校验，不由模型决定；待审批、已批准、结果未知等占用需要参与数量约束。
- 当前没有自动取消订单或直接调用平台资金、发货接口。
- 验收：超过可退余额、错误订单行、超量或跨 SKU 补发被拒绝；重复请求按对应幂等规则处理。

实现依据：[提案服务](../../app/services.py)、[补发服务](../../app/reships.py)、[补发与附件回归](../../tests/test_reships_attachments.py)。

### FR-09 审批、执行凭据与对账 · 必须

- 主管审核当前提案版本；申请人不能批准本人申请。修改对象、金额、政策或关联状态后重新核对。
- 审批通过只允许进入下一流程，不表示资金或物流动作已经发生。
- 客服在原渠道执行后登记成功、失败或未知结果及凭据；未知结果进入主管对账，不能直接重复执行。
- 执行登记使用幂等键；相同键与不同请求内容冲突。人工登记本身不独立核验外部凭据真实性。
- 验收：旧批准、订单变化、越权操作及未知结果直接重试均被拦截；对账留有操作者、时间和依据。

实现依据：[执行服务](../../app/services.py)、[对账服务](../../app/handoffs.py)、[售后回归](../../tests/test_handoffs.py)。

### FR-10 人工交接、结案与重开 · 必须

- 交接携带原工单上下文、原因、已尝试步骤、待核对事项和负责人；支持接单、记录、转派、结案与重开。
- 当前负责人负责交接中的回复和结案；主管可给出决策并派回有订单授权的客服。
- 有未完成售后或未知执行结果时，不能通过普通结案绕过处理；草稿生成不自动结案。
- 验收：非负责人不能代办；重开保留历史处理链和必要上下文。

实现依据：[交接服务](../../app/handoffs.py)、[交接回归](../../tests/test_handoffs.py)。

### FR-11 附件与对话核验 · 必须

- 保存上传原件，解析结果与原件关联；当前支持的格式、大小及内容限制由服务端检查。
- 客户文本与附件属于待核验材料，不能直接变成已发布知识、订单事实或权限指令。
- 图片不具有已接通视觉识别能力；提取失败或无法核对时交人工。对话导入先预览再提交。
- 验收：不合法格式、路径或大小被拒绝；未核验附件不能据以生成确定业务结论。

实现依据：[附件服务](../../app/attachments.py)、[附件回归](../../tests/test_reships_attachments.py)。

### FR-12 客户反馈与问题归集 · 必须

- 反馈关联具体工单、消息原文和来源快照；专题成员需要审核，支持归组、合并、拆分和撤回。
- 同一工单的多条消息不直接作为多个独立问题计算；不同型号或条件不能只因表述相近就无条件合并。
- 展示覆盖和去重计数；无销量或成熟退货分母时不显示总体退货率、缺陷率。
- 验收：操作保留前后关系；已有下游任务时，不直接改写上游归组破坏证据链。

实现依据：[改进服务](../../app/improvement.py)、[改进回归](../../tests/test_improvement.py)。

### FR-13 原因核验与改进任务 · 必须

- 一个专题可关联多个待核实原因，保留支持、反对和缺失检查；客户归因和文本共现不等于原因已确认。
- 内容缺项需版本对照；质量类原因需额外检查记录，不能仅凭对话聚类认定物理故障。
- 任务绑定专题、类型、负责人、预期改变、交付标准和可选截止日；截止日未设时明确显示。
- 客服仅处理本人任务并提交交付；主管审核交付、记录实施并决定观察或退回。
- 验收：完成任务必须有交付记录；调查可以得出无法确认，不强制产生确定原因。

实现依据：[改进服务](../../app/improvement.py)、[任务页面](../../frontend/src/TaskBoard.tsx)、[改进回归](../../tests/test_improvement.py)。

### FR-14 知识更新、回归与后续观察 · 必须

- 修改商品或政策形成候选版本，保留原文和变更依据，经规则回归及主管发布后生效。
- 历史回复保留当时来源；回滚通过新版本影响后续使用，不能重写旧记录。
- 观察记录保留实施时间、窗口、影响范围、覆盖和其他变化；没有后续案例时输出数据不足。
- 验收：回归失败不发布；来源或订单变化使在途批准重新核验；交付、发布不自动转化为经营效果。

实现依据：[知识服务](../../app/knowledge.py)、[业务观察](../../app/trial_records.py)、[知识回归](../../tests/test_knowledge.py)。

### FR-15 回答评测与运行记录 · 必须

- 错误反馈进入待审核案例，不能直接作为通过人工审核的参考答案。
- 评测保留输入、期望、来源、版本、失败与运行状态；模型硬检查通过仍需语义复核。
- 模型调用保留可取得的用量、耗时、错误和费用估计；未知用量与费用不填写成零。
- 测试集来源和历史使用情况明确，既有开发案例不能宣称独立留出数据。
- 验收：引用存在不等于事实成立；错误承诺退款、权限越界或关键条件丢失应失败。

实现依据：[评测服务](../../app/evaluation.py)、[输出检查](../../app/quality.py)、[模型回归](../../tests/test_live_model.py)。

### FR-16 备份、导出、观察计划与清理 · 必须

- 导出保留业务关联，排除认证哈希；备份与恢复需要完整性及内容核对。
- 独立业务验证工作区支持计划、来源、案例、审核、配对测量、轮次与收口记录；授权业务与本地回放分别统计。
- 到期、撤销和按提供者要求的清理只作用于其声明范围；原始资料包和既有备份需各自管理。
- 验收：不能因删除当前库记录就宣称所有历史副本已清除；不能因阶段切换就宣称已连续运行指定天数。

实现依据：[业务计划](../../app/pilot.py)、[验证工作区](../../app/trial.py)、[计划记录](../../app/trial_records.py)、[备份校验](../../scripts/check_backup.py)。

## 5. 页面与信息架构

| 入口 | 主要任务 | 关键状态 |
|---|---|---|
| 商家配置 | 初始化、人员、商品政策发布、订单导入与授权 | 空库、输入错误、预览、待审、回归、已发布 |
| 客服处理咨询 | 咨询列表、补齐条件、查看来源、编辑与记录回复 | 无咨询、缺信息、处理中、翻译中、失败、待人工、已结案 |
| 主管待办与售后审批 | 审批、未知结果对账、升级调度 | 待审批、等客服执行、待对账、版本冲突 |
| 人工交接 | 接单、记录、派回、结案与重开 | 待接单、处理中、已关闭 |
| 客户反馈与问题审核 | 原文提名、审核归组、核实原因 | 候选、调查中、合并、撤回、未确认 |
| 我的任务与改进管理 | 分派、处理、提交、验收及观察 | 草稿、进行中、阻塞、已交付、观察中、完成、重开 |
| 知识管理与服务质检 | 资料发布、回归、案例审核、失败检查 | 草稿、待审、回归失败、已发布、已替代 |
| 管理工具中的业务验证 | 计划、回放、测量、收口 | 无计划、资料未齐、数据不足、已暂停、已关闭 |

空状态说明下一步；失败保留用户输入；权限不足与版本冲突给出可继续的操作。前端状态名称以当前页面为准，接口状态以服务端返回为准。[导航实现](../../frontend/src/navigation.ts)。

## 6. AI、数据与运行约束

1. 商品事实、商家政策、客户材料和订单快照分别保留来源；客户文本及模型输出不能改变权限和审批。
2. 金额使用 decimal 与明确币种，时间包含时区；退货资格按可靠时间与适用政策计算，不直接等同于批准。
3. 当前规则服务执行查证和业务判断；可选模型主要改写受约束的回复，翻译是独立能力，不把它描述成已接入通用自主规划器。
4. 模型服务提供预算、并发、截止和停机控制。具体配置见 [模型配置](../../app/model_config.py)，不得将配置值写成实测性能或业务 SLA。
5. 列表、草稿和翻译的性能指标需在记录机器、样本与并发后测量。本版没有可公开的生产可用性、峰值吞吐或商家语义正确率承诺。
